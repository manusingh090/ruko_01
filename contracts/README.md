## POST /v1/decide

Called once, when the user taps Pay. The server answers in 200 ms or less. The client should also
give up after its own short timeout and let the payment go through (fail open, T0).

### Request
| Field | Type | Notes |
|---|---|---|
| `request_id` | string | a new UUID per Pay tap; echoed back in the response |
| `user_id` | string | demo: `u_demo_meena` |
| `payee_upi_id` | string | **plain** UPI ID (not hashed). It's needed for the NPCI / bank / registry lookups. The payee's ID is not the user's private content. |
| `amount_inr` | number > 0 | |
| `entry_method` | `typed` \| `qr` \| `contact` \| `collect` | how the payee was entered |
| `payer_says` | optional: `government` \| `company` \| `family` \| `shop` \| `investment` \| `other` | answer to "Who are you paying?" |
| `ts` | ISO 8601 **with timezone**, e.g. `2026-11-07T10:40:00+05:30` | |
| `context` | object or `null` | `null` = the user opted out of phone signals |

`context` holds only flags derived on the phone. SMS text, audio, contacts and screen content are never sent.
- `call`: `active`, `kind` (`sim`\|`voip`), `direction` (`incoming`\|`outgoing`), `caller_number`, `caller_in_contacts`, `started_min_ago`, `ended_min_ago`, `speaker_on` (c2-0.5: call audio is on the loudspeaker at the moment of Pay; `null` when no call)
- `device`: `remote_access_active`, `remote_app_installed_min_ago`, `untrusted_accessibility`, `sideloaded_last_24h`
- `episode` (c2-0.3): the task-scam episode the phone's background watcher keeps for up to 30 days across all payees and UPI apps (bank SMS + this app's payments). `state` (`none` \| `watching` \| `active` \| `dismissed`), `age_days`, `bait_credits`, `bait_inr`, `outs`, `outs_inr`, `new_payees`, `escalation_steps`, `last_out_inr`, `out_to_in_ratio`, `payee_seen_in_episode`, `rules_version`. Rules: `episode_rules.json`; shared test cases: `examples/episode_vectors.json`. Bait fields are `null` when SMS can't be read; `episode` is `null` when the watcher is off. The engine counts it as **one lure-family signal**.
- `money` (c2-0.2, **removed in c2-0.4**, now 422): the payer's own money flow over the last 72 h, counted on the phone from the app's payments and bank SMS alerts. Only counts and sums leave the phone. `bait_credits` (small credits of Rs 500 or less from UPI IDs the user never paid), `credits_inr`, `debits` (not counting this one), `debits_inr`, `new_payees`, `escalation_steps` (run of payments each at least 1.5x the one before, up to the latest), `last_debit_inr`. Credit fields are `null` when SMS checks are off.
- `lures`: list of `{tag, conf 0–1, min_ago}`. The tag is one of `arrest_threat`, `kyc`, `task_job`, `trading_tip`, `refund`, `normal`.
- `session` (c2-0.5): how the user behaved on the Pay screen of **this** payment, measured inside the app
  from opening Pay to tapping Pay. Only counts and rounded times leave the phone: never the keys typed,
  never which other app was open. `null` when the user switched "Session checks" off.

  | Field | Meaning (the phone and the simulator must measure it the same way) |
  |---|---|
  | `amount_digits` | digit key presses in the amount box (deletions not counted) |
  | `amount_median_gap_s` | median seconds between two digit presses, 1 decimal |
  | `amount_max_gap_s` | longest seconds between two digit presses, 1 decimal |
  | `amount_gap_vs_usual` | `amount_median_gap_s` ÷ this user's usual median gap (median of their last 10 completed payments, kept on the phone); `null` until 3 past payments |
  | `amount_edits` | deletions in the amount box |
  | `payee_pasted` | the UPI ID arrived in one change of 5+ characters containing `@` (a paste, not typing) |
  | `pasted_within_s_of_return` | seconds between the app coming back to the foreground and that paste; `null` if no paste or the app never left |
  | `app_switches` | times the app went to the background while Pay was open |
  | `away_s` | total seconds the app was in the background while Pay was open |
  | `pay_screen_s` | seconds from opening Pay to tapping Pay |
  | `abandoned_flows_30m` | payments the user started and left without paying in the last 30 minutes |

  The engine turns these into signs (dictated amount, pasted right after switching apps, many app
  switches, cancelled and retried, long hesitation) with the thresholds in `backend/api/policy.yaml`
  (`session:`). They count as **behaviour-family** evidence, so they can never interrupt a payment
  on their own. `call.speaker_on` only adds weight to the live-call (context) signal.

- `payee_in_contacts` (c2-0.7): `true` when the payee is a saved contact on the phone, matched by the
  mobile number it is paid by (UPI number mapper) or the number inside a mobile-style UPI ID
  (`9876543210@oksbi`); `false` when contacts were readable and nothing matched (a name-style UPI ID
  typed by hand is `false`: the phone cannot see a contact behind it); `null` when contacts cannot
  be read or call checks are off. Only this yes/no leaves the phone, never names or numbers. The
  engine treats it as **behaviour-family** evidence that only softens "new payee" (R6): a contact
  never paid is still a new payee, and it never lowers call, lure or payee-intel signals. Whether a
  payee is *known* is the server's call: the bank's history, or a payment this user completed
  (c2-0.6 outcomes).

- `device_verdict` (c2-0.8): what the phone's own model (`ml/model/artifacts/v0/device_model.json`,
  run by `signals/DeviceModel.kt`) concluded from everything it measured, including readings that
  never leave the phone (its own payment history, every lure hit). Only the conclusion is sent:

  | Field | Meaning |
  |---|---|
  | `model_version` | e.g. `device-0.1` |
  | `fraud_class` | the known scam this looks like (same names as `playbook`), or `null` |
  | `level` | `low` \| `medium` (a family is lit on the phone) \| `high` (the phone would warn) |
  | `c`, `l`, `b` | the phone's context, lure and behaviour family scores, 0–1, 2 decimals; `null` when every input of that family was unmeasured (unknown is not 0) |
  | `reasons` | up to 3 reason codes the phone chose |

  `null` when the model is missing or every Scam Shield switch is off. The engine uses `c`, `l`, `b`
  as features of the same families (`device_c` is C, `device_l` is L, `device_b` is B), so the
  verdict never lights a family the raw signals did not already speak for, and never names a
  reason on its own. `fraud_class` names the scam only when the server's rules found none.

**Unknown ≠ safe:** a signal the phone did not or could not measure must be `null` (or left out).
It must never be `false` or `0`. For example, if call-state permission was denied, send
`"caller_in_contacts": null`, not `true`.

Unknown fields are rejected with **HTTP 422**. Treat a 422 like any other failure: fail open.

### Response
| Field | Type | Notes |
|---|---|---|
| `request_id` | string | echoed |
| `tier` | `T0`–`T4` | T0 go to PIN · T1 inline tip · T2 explain card · T3 pause + trusted contact / 1930 · T4 analyst review |
| `reasons` | list of codes | show up to 3, in order; empty for T0 |
| `message_key` | string or null | `t1_tip`, `t2_generic`, `t3_generic`, or `<tier>_<playbook>` such as `t3_digital_arrest` |
| `pause_minutes` | int | 30 for T3, 60 for T4, else 0 |
| `playbook` | string or null | `digital_arrest`, `fake_customer_care`, `fake_kyc_apk`, `trading_group`, `task_job`, `refund_qr` |
| `stage` | `S0`–`S5` or null | journey stage (contacted → hooked → under control → paying → paying again) |
| `evidence_id` | string or null | id of the evidence record, if one was written |
| `fail_open` | bool | true = RUKO could not decide in time; the payment proceeds |
| `contract_version` | string | |
| `threat` | object or null (c2-0.8) | the server's threat analysis; `null` on fail open |

`threat` (c2-0.8): `score` 0–100 (`round(100 × p_scam)` from the active scorer: `lgbm-*` or
`rules-*`), `level` (`none` T0 · `low` T1 · `medium` T2 · `high` T3 · `critical` T4), `fraud_type`
(the playbook, `null` for T0) and `families` (the lit families, e.g. `["B","C","P"]`). The level
always follows the tier, so the policy (two families before interrupting) still decides; the score
only explains. Show the level and the scam type in words (Hindi + English). Showing the number lets
a scammer who controls the phone probe the engine (try amounts until the score drops), so the app
shows it only next to the level and never as a "safe below N" hint. CLAUDE.md rule 4 was changed
for this.

Reason codes: `R1_live_unknown_call`, `R2_remote_control`, `R3_mule_like_payee`,
`R4_unusual_amount`, `R5_lure_message`, `R6_new_payee_typed`, `R7_tranche_pattern`,
`R8_intel_hit`, `R9_story_mismatch`, `R10_bait_then_pay`, `R11_ring_link`,
`R12_coached_session` (c2-0.5: "you seem to be guided by someone"), `ruko_unavailable`. If the app doesn't recognise a code, it
should skip it and never show it raw.

## POST /v1/episode (c2-0.4)

Sent by the phone's watcher in the background, only on state changes and only with "Share
suspicious accounts" on. `/v1/decide` never depends on it.

| Field | Notes |
|---|---|
| `event_id` | UUID; repeats are ignored, so the phone can retry safely |
| `episode_id`, `user_id`, `ts` | `user_id` is the same id `/v1/decide` uses |
| `trigger` | `watching` \| `active` \| `out_payment` \| `bait` (new bait sender) \| `dismissed` \| `closed` |
| `summary` | the same object as `context.episode` |
| `accounts` | at most 10: `{upi_id, role: bait_sender\|payee, n, inr, first_seen_min_ago, via?, step?}`; only UPI IDs the bank SMS or the app's history named |

Reply: `episode_risk` in words (`unknown` \| `low` \| `elevated` \| `high`, two-family rule: an active
episode plus payee-family evidence on an account is `high`), `reasons`, `message_key`
(`episode_task_scam_confirmed` / `episode_task_scam_possible`), `case_id` when an analyst case was
opened. Never a score.

## POST /v1/payment/outcome (c2-0.6)

The payment id is the `/v1/decide` `request_id`: one UUID per Pay tap, kept in the phone's payment
history, the server's payment graph (`GET /v1/payments/{id}`) and the analyst console. After the
PIN or Cancel, the phone sends what happened, in the background and off the payment path; it
retries until it gets an answer. The phone's own history (encrypted, 90 days) shows every payment
with its id, Scam Shield's decision in words and this outcome.

| Field | Notes |
|---|---|
| `request_id` | the payment id: the same UUID as the payment's `/v1/decide` request |
| `user_id` | the same id `/v1/decide` uses (pseudonymised on the server) |
| `payee_upi_id`, `amount_inr` | repeated, so the payment is recorded even when its check never reached the server (timeout, fail open) |
| `status` | `completed` (PIN entered) \| `cancelled` (Cancel, or left without paying) |
| `ts` | when it was completed or cancelled, ISO 8601 with timezone |

Reply: `request_id`, the `status` the server holds (the first final status wins), `recorded`
(`false` for a repeat, a conflicting status, or another user's payment id). A completed payment adds
to the user -> payee edge's `completed` count; a cancelled one does not. Unknown fields get 422.

## For the Android app: current gaps vs `net/Models.kt`
These are what the app needs to change to stop getting 422s:
- `payee_vpa_hash` → `payee_upi_id` (plain). `PAYEE_SALT` is then not needed on the phone.
- Add `request_id` and `entry_method`. Remove `payee_typed_manually`, which is covered by
  `entry_method: "typed"`.
- Flat `context{on_call, call_minutes, …}` → nested `context.call` / `context.device` / `context.lures`.
  Field defaults should be `null`, not `false` / `true`.
- `lure_tags` → `context.lures`, each with `min_ago`.
- Response: drop `case_id`; add `playbook`, `stage`, `fail_open`, `contract_version`;
  `pause_minutes` is always present.

## Changing the contract
1. Edit `backend/schema/events.py` and bump `CONTRACT_VERSION`.
2. `PYTHONPATH=backend:ml:data python -m schema.export`
3. Update the examples here, then `pytest backend/tests`.
4. Tell the Android owner which fields changed. All of this goes in one commit (CLAUDE.md rule 8).

## Changelog
- **c2-0.8**: `context.device_verdict` (`DeviceVerdict`: the phone's model verdict, fraud class and family scores; raw readings stay on the phone) and response `threat` (`Threat`: score 0–100, level, fraud type, lit families). Engine `rules-0.7`: a WhatsApp / VoIP call whose caller cannot be seen counts as an unknown caller. The API runs the trained server model by default (`--scorer ml`, falls back to rules). Additive: c2-0.7 requests still validate.
- **c2-0.7**: `context.payee_in_contacts`. Engine `rules-0.6`: a first-time payee who is a saved contact is a weaker R6; a payee this user completed a payment to (c2-0.6) counts as known. Additive: c2-0.6 requests still validate.
- **c2-0.6**: `POST /v1/payment/outcome` (`PaymentOutcome`, `PaymentOutcomeResponse`, `c2_payment_outcome.schema.json`). The `/v1/decide` `request_id` is now the payment id. Additive: c2-0.5 requests still validate.
- **c2-0.5**: `context.session` (`SessionSignal`), `call.speaker_on`, reason `R12_coached_session`. Additive: c2-0.4 requests still validate.
- **c2-0.4**: `POST /v1/episode` (`EpisodeEvent`, `EpisodeAccount`, `EpisodeEventResponse`, `c2_episode.schema.json`), reason `R11_ring_link` (payment graph), `context.money` removed. Rules `episode-0.2`: only payments above Rs 500 to payees not paid before the episode count as episode payments.
- **c2-0.3**: `context.episode` (`EpisodeSignal`), shared `episode_rules.json` and `examples/episode_vectors.json`. `context.money` deprecated (still accepted). The engine no longer lets one phone summary light two families.
- **c2-0.2**: `context.money`, reason `R10_bait_then_pay`.
- **c2-0.1**: nested `context.call` / `device` / `lures`, plain `payee_upi_id`.
